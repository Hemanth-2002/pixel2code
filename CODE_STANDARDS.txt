CODE STANDARDS AND BEST PRACTICES
==================================

This file contains project-specific coding standards, conventions, and best practices.
All code must strictly adhere to these rules.

DIRECTORY STRUCTURE
-------------------
- Components: src/components/
  - One component per file
  - File name matches component name (PascalCase)
  - Example: ProductCard.tsx contains ProductCard component

- Data: src/data/
  - Mock data, constants, and static data files
  - Use .ts extension for TypeScript data files

- Context: src/context/
  - React Context providers and hooks
  - Example: CartContext.tsx

- Types: src/types/ (if needed)
  - Shared TypeScript interfaces and types

REACT BEST PRACTICES
-------------------
1. **Component Structure:**
   - Use functional components with hooks (no class components)
   - Export default for components
   - Use named exports for utilities and types
   - Component files: PascalCase (e.g., ProductCard.tsx)

2. **TypeScript:**
   - Always use TypeScript for all .tsx and .ts files
   - Define proper types/interfaces for props
   - Use React.FC or explicit function typing
   - Example: const Home: React.FC = () => { ... }

3. **Hooks:**
   - Use useState for local component state
   - Use useEffect for side effects (with proper dependencies)
   - Use useContext for shared state (if needed)
   - Keep hooks at the top of component, before any logic

4. **State Management:**
   - Prefer useState for component-local state
   - Use React Context only when state needs to be shared across multiple components
   - Keep state as close to where it's used as possible
   - Use proper TypeScript types for state

5. **Props:**
   - Always type props with interfaces or types
   - Use destructuring for props
   - Example: interface ProductCardProps { product: Product; }

6. **Event Handlers:**
   - Use descriptive names: handleClick, handleChange, handleSubmit
   - Use arrow functions for inline handlers when simple
   - Extract complex handlers to named functions

7. **Imports:**
   - Group imports: React first, then third-party, then local
   - Use absolute imports when configured, otherwise relative
   - Example:
     import React, { useState } from "react";
     import { Box, Button } from "@mui/material";
     import { Product } from "../data/mockData";

8. **Component Organization:**
   - Keep components small and focused (single responsibility)
   - Extract reusable logic into custom hooks
   - Extract complex JSX into smaller sub-components if needed

MATERIAL-UI (MUI) BEST PRACTICES
--------------------------------
1. **Component Usage:**
   - Always use Material-UI components from @mui/material
   - Use @mui/icons-material for icons
   - Prefer MUI components over custom HTML elements when available

2. **Styling:**
   - Use sx prop for styling (preferred method)
   - Use theme for consistent colors and spacing
   - Example: sx={{ p: 2, backgroundColor: "primary.main" }}

3. **Layout:**
   - Use Box for layout containers
   - Use Container for page-level containers
   - Use Grid or Stack for responsive layouts

4. **Consistency:**
   - Follow Material Design principles
   - Use theme colors (primary, secondary) from App.tsx
   - Maintain consistent spacing using theme spacing units

5. **Components to Use:**
   - Box, Container, Paper for layout
   - Typography for text
   - Button, IconButton for interactions
   - Card, CardContent, CardMedia for product displays
   - Dialog for modals
   - Drawer for sidebars
   - TextField, Select, Checkbox for forms

TAILWIND CSS BEST PRACTICES
---------------------------
1. **Usage:**
   - Tailwind is available but Material-UI sx prop is preferred for styling
   - Use Tailwind utility classes for quick styling when MUI doesn't provide needed utilities
   - Prefer MUI sx prop over Tailwind when using MUI components

2. **When to Use Tailwind:**
   - For custom components not using MUI
   - For utility classes (e.g., flex, grid, spacing)
   - For responsive design utilities
   - Example: className="flex items-center gap-2"

3. **Tailwind Classes:**
   - Use utility-first approach
   - Combine classes logically
   - Use responsive prefixes (sm:, md:, lg:) when needed
   - Example: className="w-full md:w-1/2 lg:w-1/3"

4. **Avoid:**
   - Mixing Tailwind with MUI sx prop unnecessarily
   - Creating custom Tailwind classes (use utilities instead)
   - Overriding MUI component styles with Tailwind unless necessary

NAMING CONVENTIONS
------------------
1. **Files:**
   - Components: PascalCase (ProductCard.tsx)
   - Utilities: camelCase (formatPrice.ts)
   - Constants: UPPER_SNAKE_CASE (API_BASE_URL.ts)
   - Types/Interfaces: PascalCase (Product.ts)

2. **Variables:**
   - camelCase for variables and functions
   - PascalCase for components
   - UPPER_SNAKE_CASE for constants
   - Examples:
     - const productName = "Shoes";
     - const ProductCard = () => { ... };
     - const MAX_ITEMS = 100;

3. **Functions:**
   - camelCase for regular functions
   - handle prefix for event handlers (handleClick)
   - get prefix for getters (getTotalPrice)
   - is/has prefix for booleans (isLoading, hasItems)

4. **Props:**
   - camelCase for prop names
   - Descriptive names (product, onAddToCart, isLoading)

CODE ORGANIZATION
-----------------
1. **File Structure:**
   - Imports at top
   - Types/interfaces after imports
   - Component definition
   - Helper functions before return
   - JSX return statement

2. **Component Template:**
   ```
   import React, { useState } from "react";
   import { Box, Button } from "@mui/material";
   import { Product } from "../data/mockData";

   interface ComponentProps {
     // props definition
   }

   const Component: React.FC<ComponentProps> = ({ prop1, prop2 }) => {
     // hooks
     const [state, setState] = useState();

     // handlers
     const handleClick = () => { ... };

     // render
     return (
       <Box>
         {/* JSX */}
       </Box>
     );
   };

   export default Component;
   ```

3. **State Management:**
   - Declare all useState hooks at the top
   - Group related state together
   - Use descriptive state variable names

PERFORMANCE BEST PRACTICES
--------------------------
1. **React:**
   - Use React.memo() for expensive components (if needed)
   - Avoid creating functions/objects in render
   - Use useMemo/useCallback only when necessary (not prematurely)

2. **Rendering:**
   - Keep render functions pure
   - Minimize re-renders by proper state management
   - Use keys properly in lists

3. **Imports:**
   - Import only what you need
   - Avoid importing entire libraries when possible

ERROR HANDLING
--------------
1. **TypeScript:**
   - Always handle potential undefined/null values
   - Use optional chaining (?.) when appropriate
   - Use type guards for type narrowing

2. **User Experience:**
   - Provide meaningful error messages
   - Handle edge cases (empty arrays, null values)
   - Show loading states when appropriate

COMMENTS AND DOCUMENTATION
---------------------------
1. **Comments:**
   - Focus on "why" not "what"
   - Add comments for complex logic
   - Keep comments up-to-date with code

2. **Code Clarity:**
   - Write self-documenting code with clear variable names
   - Prefer clear code over comments
   - Use TypeScript types as documentation

GIT AND VERSION CONTROL
------------------------
1. **Commits:**
   - Use clear, descriptive commit messages
   - Format: "<TICKET-ID>: <brief description>"
   - Keep commits focused on single changes

2. **Branches:**
   - Create branch from main: git checkout -b <ticket-id>
   - Use lowercase with hyphens: scrum-9, feature-123

TESTING
-------
1. **Manual Testing:**
   - Test all user interactions
   - Test edge cases (empty states, null values)
   - Test responsive design (mobile, tablet, desktop)

2. **Code Quality:**
   - Run `yarn lint` before committing
   - Run `yarn build` to check for TypeScript errors
   - Ensure no console errors or warnings

SPECIFIC PROJECT RULES
----------------------
1. **Material-UI First:**
   - Always prefer MUI components over custom HTML
   - Use MUI theme and sx prop for styling
   - Follow existing MUI component patterns in the codebase

2. **TypeScript Strict:**
   - All files must be TypeScript (.tsx or .ts)
   - No any types unless absolutely necessary
   - Proper typing for all props, state, and functions

3. **File Organization:**
   - One component per file
   - Related files in same directory
   - Keep components in src/components/

4. **State Management:**
   - Use useState for local state
   - Use Context only when state needs to be shared
   - Keep state management simple and clear

5. **Styling Priority:**
   1. Material-UI sx prop (preferred)
   2. Material-UI theme
   3. Tailwind utility classes (when MUI doesn't suffice)
   4. Custom CSS (avoid unless necessary)
